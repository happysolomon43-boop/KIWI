# Delivery 6 — task participation, interpretation and adaptation

Delivery 6 has an implemented, inactive candidate on `feat/classroom-remodel-delivery-6`, stacked on Delivery 5 through draft PR #334. Its native and browser evidence uses synthetic academic providers and identity with actual PostgreSQL, authenticated routes and the mounted classroom UI. This is not live-provider qualification or a production rollout. The owner-policy, prompt/provider/reviewer and coordinated migration gates remain open. All 44 blueprint qualification scenarios retain `NOT_QUALIFIED` status.

## Task contract and participation

The coordinator's registered `design_check` contract separates public question text from immutable private criteria and accepted alternatives. Acceptance checks the exact owned Course Learning Unit, chapter objective/version and anchors, evidence intent, inference ceiling, assistance ceiling, demand vector, modality, validation receipt and owner-adopted duration. Unsupported modalities and formal measurement stay with established owners. Independent validation is required where the content owner says external validation is mandatory.

One blocking window is persisted per session. A pending question opens only when every portion in its sequence has an active accessible render receipt. Board objects and required assets remain part of presentation readiness. The server commits the opened time and absolute deadline. Insufficient fair remaining time produces a system cancellation, never a wrong answer. Extensions are bounded changes to the same window/version and do not exceed Class end. Pause, pace, reload and device takeover do not grant extra time.

The existing authenticated Class router provides `task-responses`, `task-extensions` and `task-support`, plus compatible `tasks/:taskId/responses`, `tasks/:taskId/extensions` and `tasks/:taskId/support` aliases. A task identifier in the URL must match the command body. Responses bind the exact session, task version and window version; browser timing, authority and charge fields are rejected.

The existing presentation authority transaction commits a stable D12 response identity, immutable task/source/guide/criterion/exposure context, window transition, conversation event, evaluation job and idempotent receipt together. Independent connections serialize against the existing owner locks. Identical retries replay the original receipt; changed operations conflict. A scheduling failure rolls the entire admission back. Accepted work survives delayed acknowledgements, closure and protected takeover. No response becomes `EXPIRED_NO_RESPONSE` without an incorrect evaluation.

The mounted response form includes a task-specific draft, server deadline, submission, extension, help and clarification controls. Drafts and uncertain requests retain the original command/key for the adopted retention period. Reload offers an explicit acceptance check. Known rejection preserves the draft. Owned committed receipts can be rechecked after closure; protected views suppress instructional content. Requested responses, task help and extensions do not use discretionary conversational allowance.

## Interpretation, public feedback and one action

The candidate coordinator uses `interpret_response` through the existing D03/D05 execution mechanism and existing response-evaluator capability. Candidate invocation remains qualification-only. The original active prompt bindings are retained.

Canonical findings remain intact alongside the conservative D12 compatibility projection. Item validity is considered before negative attribution. Correctness, concept, reasoning, completeness, alignment, independence and sufficiency remain separate. Partial success, valid alternatives, local slips, uncertain misconception/prerequisite hypotheses, accommodations and evidence limits survive projection. Accessible chapter answers and uncertain exposure cannot establish independence or mastery.

An evaluation acceptance receipt binds the immutable admission/context/output and a particular evaluation identity. Evaluation work has adopted leases, retry limits, backoff and timeout; a late worker cannot commit against a fenced lease. The owner bounds the proposal to one accepted action and records why a conflicting proposal was constrained. No official grade, mastery state or Controller transition follows from this evaluation.

An independent owner selects public-safe feedback before Presenter generation. Raw diagnostics, expected answers and private criteria stay with the evaluator/reviewer. A separately reviewed Presenter turn binds the task, accepted evaluation receipt, authority and delivery epoch. Publication and accessible confirmation are separate from preparation. Feedback does not complete handling merely because a model generated it.

Confirmed feedback creates a durable adjustment obligation. Unrelated teaching stays held until the one accepted adjustment is handled. A fresh check requires independent construct-preserving variation review, explicit original-task lineage and rejection of cosmetic replacement. Its design, private criteria, Presenter question and next render-gated window use the same owner contracts. Significant replanning invokes the trusted TPF-05/D11 path with actual work; immediate instruction is realized within the accepted feedback permissions. A stale rejected question cannot be recorded as an applied adjustment.

## Assistance and recovery

The eight existing D12 assistance levels and task ceiling constrain all help. Repeated requests do not increase the ceiling. Immutable exposure entries distinguish prepared, released and accessibly confirmed assistance. Accessible chapter content remains conservatively recorded; uncertain access is not upgraded to independent evidence. Selected hint wording is independently reviewed and published through the existing presentation engine. Help preserves the original response deadline.

Support acceptance stores its own identity and durable due event. It promises saved task-related support, not an uncommitted appointment or automatic extension. The existing event runtime owns processing and retries; no second queue or worker infrastructure is introduced.

## Corrections and atomic replanning

Accepted corrections refer to an owned published original portion. An explicit successor retains its versioned original link. Board repairs add owned successors and preserve original Board history; the conversation retains the old Board reference. D12 records a correction and evidence-owner recheck handoff without modifying official outcomes. A correction report's queue hold clears only when its reviewed correction is accessibly confirmed.

Unresolved source conflict is persisted and holds future release. A confirmed academic-source error requiring a revised chapter becomes a durable owner handoff: affected pending/open tasks are cancelled as system outcomes, prepared output is invalidated, and the existing chapter is retained until a separately validated compatible chapter/guide/plan/remap bundle exists. This candidate does not silently rewrite a live academic source or claim that source revision has completed.

Substantial and lateness replans accept only complete, reviewed TPF-05 artifacts. The request binds actual confirmed teaching, accepted responses, accepted evaluation identities, strategy history, unresolved questions, task windows, current position and remaining authoritative time. D11's existing live-replan validator protects unfinished CORE objectives and adopts its reserve policy. The accepted plan artifact is source-compatible. One transaction creates the D11 blueprint and preparation-binding history, advances the owned session pin, invalidates prepared sequences/turns and advances delivery authority. Completed teaching, accepted work, chapter version and open response deadline remain intact.

The former unconditional binding-pin rule now has a narrow audited D11 exception for accepted plan/blueprint advancement. Chapter and policy pins remain protected; arbitrary session/delivery pin mutations still fail. Revision content, turn content and completed action outcomes are immutable; lifecycle fields can advance without rewriting historical provenance.

## Post-closure reconciliation

D12 has a separate immutable-admission evaluation path. Its legacy live guard was not relaxed. Previously accepted work can finish evaluation after closure under its original task/source/exposure context. That path cannot reopen the Class, publish live feedback or continue teaching. Delivery 7 can consume the accepted evaluation versions and outstanding work without treating them as feedback delivered during the Class.
